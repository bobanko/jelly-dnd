# Jelly & Bones

## Генерация звуков через ElevenLabs

Локальная утилита использует официальный [Sound Effects API](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert). Ключ не используется браузером: в игру входят только готовые аудиофайлы.

1. Создайте API-ключ в [ElevenLabs](https://elevenlabs.io/app/developers/api-keys) с доступом к Sound Effects. Для проверки подключения через `/v1/user` также нужен доступ User Read.
2. Скопируйте `.env.elevenlabs.example` в `.env.elevenlabs` и заполните `ELEVENLABS_API_KEY`. Если локальный файл уже создан, просто вставьте ключ после `=`. Не отправляйте ключ в чат. Файлы `.env*` исключены из Git и недоступны через сервер разработки; сборка использует отдельный список игровых файлов.
3. Выполните `npm run audio -- --check`. Проверка делает только запрос данных пользователя, не генерирует звук и не выводит данные аккаунта. Доступ именно к Sound Effects проверяется при первой генерации.

```sh
npm run audio -- --list
npm run audio -- jelly-land --dry-run
npm run audio -- jelly-land
```

Пресеты `jelly-death`, `jelly-land`, `spikes` (выдвижение), `spikes-retract` (втягивание), `portal` и `dungeon-wind` находятся в `scripts/sound-effects.json`: там можно менять описания, длительность (0.5–30 секунд), `prompt_influence` (0–1) и зацикливание `loop`. `--dry-run` показывает запрос без ключа и обращения к API. Обычный запуск генерирует один эффект и расходует кредиты аккаунта; автоматических повторов запроса нет. Используются модель `eleven_text_to_sound_v2` и MP3 44.1 kHz / 128 kbps.

Результаты сохраняются с уникальными датированными именами в `assets/audio/`, без перезаписи предыдущих вариантов. Утилита не подключает эффекты к игровым событиям автоматически. В игре уже подключён пробный набор: гибель (разбивающееся яйцо), приземление, портал, выдвижение/втягивание шипов и тихая петля ветра. Включите звук кнопкой динамика; в меню и при скрытой вкладке эти дорожки останавливаются. Файлы и громкость задаются в `game-audio.js`. Новые генерации нужно выбирать там вручную. Переменная окружения `ELEVENLABS_API_KEY`, если задана, имеет приоритет над локальным файлом.

Проверка утилиты без сети и кредитов: `node --test tests/elevenlabs.test.js`.

## Сборка для itch.io

Запустите `npm.cmd run build` (на macOS/Linux — `npm run build`). Команда проверяет синтаксис и карты, затем создаёт `dist/jelly-and-bones-itch-YYYY-MM-DD_HH-MM-SS.zip`. Дата и время — по Киеву. Каждая сборка сохраняется отдельным архивом; при совпадении секунды добавляется числовой суффикс.

Загрузите ZIP в проект itch.io с типом HTML и отметьте **This file will be played in the browser**. `index.html` уже находится в корне архива. После изменений кода или JSON-карт повторите команду и замените загруженный ZIP.

Основной размер встраиваемого окна — **960 × 640**. Укажите эти размеры на itch.io; игра также подстраивается под изменение окна и полноэкранный режим. Для проверки английского и русского интерфейса в этом размере есть `npm run test:layout:browser`.

В архив входят игра, редактор, каталог и карты из `levels/`, используемые ресурсы из `assets/`. Сервер, Node-зависимости, тесты, Git и локальные служебные файлы исключены. Сборка использует только встроенные возможности Node.js.

Для локальной проверки распакованного билда можно запустить `tests/browser-static-host.js` с переменной `STATIC_GAME_ROOT`, указывающей на папку распаковки (для этого теста нужны установленные dev-зависимости и Chrome). Игра требует браузер с WebGPU и рабочим аппаратным ускорением.

A dungeon puzzle with one to five translucent jelly creatures and movable wooden crates. The original chamber uses three creatures; edited maps choose their own party. Version 0.2 replaces the projected Canvas/WebGL scene with a real 3D WebGPU scene and tetrahedral soft-body physics. The visual and physical requirements in jelly-dice.md are adapted to the existing game without dice rolling, dice scoring or table-demo mechanics.

## Run

All unit tests, browser checks, and profiling scripts live in [`tests/`](tests/README.md). Run npm commands and individual test scripts from the project root; generated output stays in `artifacts/`.

The development environment uses Node.js 26.7.0 (the current minimum is 22.13). Browser code, tests, server code, and release tooling use native ES modules with `import`/`export`; `package.json` declares `type: module`. Browser runtime files are served directly without bundling.

Run npm start (or node server.js), then open http://localhost:3000 in Chrome or Edge with WebGPU enabled. No runtime packages, CDNs or external fonts are needed. Stone and oak textures are bundled in assets/materials/; their generation prompts and mapping details are documented there. Serve over localhost or HTTPS; opening a local HTML file is not the supported launch path.

If the browser has no WebGPU adapter, an explanation appears instead of a blank scene. A lost GPU device also shows the fallback card. There is no silent return to the old 2D renderer.

Each level opens with a two-second assembly: stone and coloured blocks arrive in sequence from the screen edges, above and below, with low arrivals emerging through the void fog. The GPU moves blocks and their shadows without changing physics geometry. Characters, mechanisms and decor appear once assembly finishes; hazards and the run timer remain paused until then. A movement key skips assembly, and reduced-motion settings show the completed level immediately. Restart does not replay the animation. `npm run test:assembly:browser` checks the construction frames, coloured blocks, pause, skip and reduced-motion paths on WebGPU.

Place, select, move and delete objects directly in the scene. The editor has no 2D mode or view switch. Every cube has independent integer X/Y/Z coordinates; several may share X/Z while occupying different Y layers. Y ranges from -2 to 12. Old floor columns and wall slabs become individual cubes when opened/imported in the editor; torches are separate wall decorations.

Rounded luminous edges, polished reflections, small glass inclusions and a faint inner flow follow the energy-block reference while keeping characters and terrain visible through the faces. A soft coloured glow pools on a supporting surface below. The same material appears in the game and 3D editor; palette symbols match the energy blocks. Only the matching hero passes through the entire volume, including its floor and ceiling. Other heroes, crates and arrows still collide with them. Choose a colour in the block inspector to recolour an existing cube, or select Ordinary stone to restore it. Colour brushes support face/layer/XYZ placement, rectangles, history and JSON export. Optional `blocks[].color` is the hero slot (0–4); omitted means ordinary stone. Validation rejects spawns/finishes supported only by their own pass-through colour.

Drag a brush or rectangle to build a row or platform on one layer. The XYZ panel places a cube directly; selecting an existing cube exposes editable X/Y/Z fields and the move action. Shift+left-click, the eraser and Delete remove the picked layer rather than the whole column. Wire outlines preview placement, and brush strokes update the 3D scene before mouse-up.
- Place any one to five coloured spawns and their matching rune finishes: Moss (green), Frost (blue), Ember (red), Amethyst (purple), Amber (yellow). Spawns determine the participating characters; unused colours need no markers. Every participating colour needs its own finish. Extra finish tiles may remain on the map; they stay inactive and do not block victory. A colour's existing spawn/finish moves when it is placed again. Select a cell to inspect its objects, change properties, remove an individual object or move it to a new cell.
- The palette uses coloured icons grouped by object type, with names available on hover and through accessible labels. Portal colours include green, blue, red, purple and amber; each colour forms its own independent chain. Place buttons, sliding bridges, lifts, conveyors, timed spike traps, coloured portal chains, crates, skeleton archers, shields and swords. Objects create a floor underneath when necessary. Crates may share a button tile. Surface mechanisms replace other surface mechanisms on the same tile.
- Spike brushes choose a neutral or character colour and a mounting face. In 3D, “По грани” attaches them directly to a clicked top or side face; explicit floor/north/east/south/west mounts also work on the selected construction layer. The inspector edits colour, mount, anchor Y and timing. Wall traps belong to a block's side at its middle height, with up to four independent side mounts and a floor mechanism on the same block. Each mount has four individual sockets without a shared stone tile.
- Conveyors have four cardinal directions and a speed of 0.2 to 2.5 cells per second. Set these before painting or edit an existing tile's properties. Brush strokes and rectangles can create long connected belts; neighbouring tiles with the same direction and floor height share continuous rails and moving chevrons.
- Select a bridge's controlling button in its properties. Connections use stable button IDs, so moving a button or reordering the array preserves the link. Deleting a button leaves a visible validation error until the bridge is relinked. Connection lines and channel numbers appear over the 3D scene.
- Mechanisms, spawns, finishes and props are attached to the selected cube surface and store their own Y. Set lift base/top levels, spike phase delay, portal colour, archer facing, firing interval and initial delay. Mechanisms can occupy different storeys in one X/Z column. New objects create only their supporting cube when necessary.
- Right-drag rotates the 3D camera freely and adjusts its tilt, with the same smooth easing as the game. Middle-drag or Space+drag pans; the wheel zooms. Dedicated pan/orbit tools also work with left drag or touch. Choose isometric or perspective projection, turn the construction grid/connections on or off, and inspect collider outlines. Q/E and the rotation buttons turn smoothly by 90 degrees. Bridges are displayed extended for editing; gameplay starts with them retracted. Camera gestures leave map history unchanged.
- Ctrl+Z undoes a complete brush/rectangle gesture; Ctrl+Y or Ctrl+Shift+Z redoes it. V selects, B paints stone, X erases, M selects the pan tool, and F fits the view. Hold WASD or the arrow keys to move the view in 3D, relative to the screen. Space+drag or the middle mouse button also pans; the wheel zooms. The pan tool and explicit +/− buttons also work on small touch screens. Ctrl+S saves, including when a property field is focused. Shortcuts use physical key positions and work with Russian layouts. Camera shortcuts are ignored while editing fields; Up/Down in a numeric field changes integer properties by 1 and fractional properties by 0.1, preserving focus across inspector updates.

Draft edits autosave in this browser under jelly-dnd.editor.v1. Export downloads a versioned JSON level file; Import loads such a file after validating its structure. Import, a new map, resizing and opening a campaign map can all be undone. File errors leave the current draft intact. The grid can be resized from 8×8 to 16×16; shrinking removes out-of-bounds objects and can be undone.

Play validates the map, saves a separate playtest copy under jelly-dnd.play.v1, and opens /?level=editor. Missing or obstructed spawns/finishes, missing floors, single-portal chains, invalid lift heights and dangling bridge links are reported before launch. The game loads this exact shared map format and derives player/crate spawn heights from the surfaces. Reset preserves those heights. The game header returns to the editor; playing never modifies the draft. Opening the ordinary game URL loads the first campaign map.

Map files contain initial definitions only, not live velocities, health, collected items or timer state. levels.js owns parsing, validation, migration, the original chamber and runtime construction; editor-model.js owns reversible editing operations.

## Play

- Movement controls follow the active characters' order, independently of their colours. One character accepts WASD, arrow keys, IJKL, TFGH and NumPad 8/4/5/6. With two characters, the first uses WASD or TFGH and the second uses arrows, IJKL or NumPad. With three to five characters, their primary sets are WASD, arrows, IJKL, TFGH and NumPad (8 forward, 4 left, 5 back, 6 right). The HUD shows the actual assignments. Movement is continuous, diagonals and simultaneous character control are supported; physical key positions work across keyboard layouts.
- All shortcuts use physical KeyboardEvent.code positions, including on Russian keyboards.
- Q/E rotates either camera by 90 degrees. 1/2/3/4 follows the corresponding green/blue/red/purple character when present. Both projections smoothly track the character in X/Y/Z, including lift rides, drops, lower floors and respawn. Switching characters eases to the new height; restart initializes the camera at the spawn's height. The HUD shows participating characters only. The wheel zooms.
- Open Settings to switch between perspective (default: 55° downward angle, 45° vertical FOV) and orthographic isometry (30°). Pitch adjusts from 25° to 80°; FOV from 25° to 85°, enabled for perspective. FOV adjusts perspective strength with a compensating camera distance, preserving the apparent scale at the followed jelly's centre, including on the upper terrace. The wheel changes zoom independently. Each mode remembers its own pitch during the session. Restarting the puzzle keeps camera settings. Perspective refraction uses per-pixel viewing rays; picking and rendering share the same projection matrix.
- Z undoes a movement gesture or poke, including the complete deformed lattice, falling and death. R restarts.
- Victory requires every participating jelly to remain settled on its own finish for three uninterrupted seconds. A clockwise seal surrounding each active finish and its four matching runes fill with light together; the engraved tile rune also brightens as it is inscribed. Controls and physics remain active. Leaving a finish, dying or losing the correct height resets the whole countdown; re-entry starts a fresh three seconds. Reset and undo also clear it. The victory window, sound and bright beams appear only after the full hold.
- Click a cube to poke its actual physical surface. Open the jelly controls to change softness, wobble damping or inspect the tetrahedral lattice.
- In the same panel, the separate level-collider checkbox displays floor/wall boxes, moving lift bounds, spike triggers and portal triggers. This is independent of the creature lattice overlay.
- Sound starts off. It can be enabled with the top-right button.
- Losing focus clears movement and horizontal velocity. Reduced-motion mode removes camera interpolation and ambient material animation; gameplay physics remains active.

Stand on the golden plate to raise the opposite bridge. Moss opens the route for Frost and Ember; Frost's destination plate opens Moss's route. All three must stop on their matching runes. Cubes can push each other over an open edge. The falling creature dies and respawns individually; the others remain playable. Occupied starting positions use a nearby free tile. A powered bridge holds a grounded cube until it leaves; an unpowered bridge is a hole.

Bridges are full oak decks assembled from separate crosswise boards, under-deck beams and iron end brackets. They remain visible hanging vertically from the northern hinge while inactive, then unfold through 90 degrees as one mechanism when a plate is held; no geometry or wood texture grows out of a bank. A critically damped spring smooths starts, stops and reversals in roughly one second. Floor support and the debug collider appear only when the deck is close enough to horizontal to be safely walkable. Undo restores angle and movement velocity, while reset folds both bridges down. Moving bridge meshes are separate from cached static dungeon geometry.

Bridge material uses the same compact colour choice as level cubes: the ordinary swatch creates a classic wooden deck, while any jelly colour creates a thin spectral slab. Spectral bridges reuse the colour-block rule: a matching-colour jelly passes through, while other jellies and crates can cross. Their translucent rim remains visible as the complete deck rises, and three copies of that colour's finish glyph continuously drift upward above it.

Pressure plates consist of a circular coloured button and its dark metal rim/socket, seated directly on their supporting surface without a separate square stone tile. The bevelled button depresses smoothly under a jelly or crate, then rises on release; colour is retained in both states. The surface reuses the bundled stone atlas with a coloured material. Rims and buttons are cached geometry, and button movement updates only its transform without rebuilding dungeon decorations. The colours are identifiers; any supported body can activate either plate.

## Lifts, hazards and portals

Conveyors gradually carry grounded jellies and crates, including passengers riding on them. Movement input adds to the belt velocity, so characters can walk across or against the belt. Partial footprint contact blends the force at entry and exit; adjacent tiles preserve transport across their seam. Walls still stop bodies, and an unguarded belt can push them off an edge. A short eastbound example occupies (1..3,10) in the original chamber. Conveyors reuse floor colliders and cached decoration geometry; their surface pattern animates in the existing material shader.

The demonstration level has a gold-framed lift at (5,7) and a 3 by 3 upper terrace at (5..7,8..10), one world unit above the lower floor. A wooden crate starts at (7,9); push it east to drop it onto the lower floor. Stand on the lift and pause briefly to board it. It raises the complete physical lattice and any supported passengers by one unit; walk toward the terrace to step off. An empty lift waits briefly, then returns down automatically.

Short spikes at (3,9) and (9,6) follow a 5.8-second cycle: two seconds raised, a 0.3-second descent, 2.2 seconds fully hidden, one warning beat showing harmless tips, then a 0.3-second full rise. The warning first reveals 30% of the spike over 0.15 seconds, then holds that position until the next beat. The traps are offset by 2.9 seconds. There is no coloured indicator; the visible tips provide the warning. The trap becomes lethal above 35% extension, including when a creature is pushed onto it; hidden and warning stages are safe. Rendering, damage and the debug trigger use the same physical clock and extension. Undo rewinds the trap cycle and reset restarts it. Only the affected creature respawns. Held input for a killed creature is cleared so it cannot repeatedly walk into the trap during respawn.

Button-linked spikes start hidden and smoothly extend over 0.3 seconds while their button group is pressed. Releasing the group retracts them at the same rate; pressing or releasing midway reverses the motion from its current position. They use the same 35% damage threshold, so stepping onto a button cannot cause damage from still-hidden spikes. Motion sounds follow each rise and retraction, and undo restores the intermediate position and direction.

Each trap has four square-pyramid spikes in individual square metal rims, seated directly on the supporting surface without a shared base. Rims match their spikes' colour and remain visible during full retraction, so the trap's colour can be read in advance; neutral rims are silver-grey. Neutral silver spikes hurt every jelly; a coloured spike is harmless only to the jelly with the same colour identity, including sparse parties. Floor spikes point upward; wall spikes project out of the selected block face. All five orientations share mount transforms for rendering, trigger contact, debug volumes and editor picking. Spikes slide into their sockets during retraction rather than deforming. Old maps default to neutral floor spikes. Optional `spikes[].color` is a hero slot 0–4 and `face` is `north`, `east`, `south` or `west`; omitted means the top surface. For wall mounts, integer `y` identifies the supporting block's top layer.

Spike deaths and falls into the void scatter the same glossy jelly scraps from the actual deformed lattice. They fall, bounce on surfaces crossed from above and fade before respawn. Fragments below the level keep falling instead of snapping to the floor above them. Portal traversal emits matching expanding rings, a brief flash and rising sparks at both endpoints, including their floor heights. These bounded, transient visual particles do not participate in character collisions; reset and undo clear them. Reduced-motion settings shorten the effects and remove portal sparks.

Violet floor portals link (3,6) and the upper terrace at (6,9). Amber portals link (9,9) and (7,2). Any creature can use either colour. Each colour forms a directed cycle in placement order: 1 → 2 → 3 → 1, with any number of members from two up to the shared 64-portal map budget. Each portal transfers the whole deformed lattice and skull, adjusts floor height and clears momentum. The destination remains locked until the creature fully leaves it, preventing repeated teleporting. A blocked next destination is never skipped. Crates, characters and solid terrain block an exit, and the waiting source resumes as soon as it clears. Separate colours and floor heights remain independent. The editor shows numbered arrows and a per-portal chain-order field; repainting an existing portal with the same colour preserves order. Reordering, moving, deleting, undo/redo and JSON roundtrips retain the cycle.

The portal swirl and rim brighten smoothly as a living creature's footprint moves over the opening, with a matching coloured glow on the surrounding floor. Activation, blocking, clearing and approach brightness ease over roughly half a second; rim, vortex colour, floor halo and rising-ring opacity change together. Vortex speed is integrated continuously, so changing state or reversing midway never jumps its phase. Transport availability changes immediately, independently of the visual fade. Reduced-motion mode updates the state directly. Unavailable portals become a muted grey with a faint hint of their original colour, a slowly moving swirl and a soft floor halo, while rising rings disappear. This includes arrival-locked portals and sources whose next destination is blocked: both ends of a pair dim together. An arrival stays locked while its jelly partly overlaps the portal slab; normal colour and effects return after full clearance. In longer chains, the unavailable portal and its immediate predecessor dim, while other usable links remain active. Availability is checked independently for sending and receiving, so an entrance waiting for its own next exit can still receive a visitor if its landing space is clear. Three translucent rings rise, expand and dissolve above active portals. Their mesh is cached once and instanced; the GPU animates height, radius and opacity. The glow and rings share the final jelly render pass instead of adding another full-screen resolve. Reduced-motion mode keeps the ambient rings stationary. Cubes on another floor and crates do not charge portals.

A skeleton archer stands at (10,5), facing south along the x=10 grid lane. It fires every 2.4 seconds and draws its bowstring during the last 0.65 seconds before each shot. Arrows travel on a single cardinal axis without tracking targets. Swept segment collisions stop them at the nearest wall, raised terrain, crate, shield or creature, including during fast frames. An unprotected hit shatters and respawns the jelly. The skeleton has a solid level collider visible in the collider overlay.

An oak shield lies at (8,8), and an iron sword at (8,7). A living jelly with a free equipment slot automatically picks up either item by approaching on the same floor. Equipment and a small bone arm attach to the front face, turning to the last movement direction in world space, including after camera rotation. Facing persists while stationary; equal diagonal inputs retain a compatible current face.

The shield blocks three frontal arrows. Each hit scores the wood; the third hit is still blocked but breaks the shield into fading wooden splinters. A fourth arrow can then kill the unprotected jelly. Side and rear hits bypass the shield. Block sounds combine a low wooden thud with short filtered noise cracks; the former block tone now plays when the skeleton fires. A broken shield stays destroyed until reset or undo. An intact shield returns to its pickup when its owner falls or dies, retaining its remaining durability.

Pushing another jelly with the shield launches it in a physical arc over one intervening cell, travelling roughly two cells on level ground. The flight uses gravity and normal terrain/body collisions, so it can cross a one-cell hole, strike a wall or land on another surface. Movement input cannot steer the passenger during the throw; its equipment stays attached. Releasing controls or changing the camera does not cancel the flight.

The sword automatically swings at a skeleton directly in front within reach, on the same floor and with no intervening wall. The skeleton collapses into bone fragments, loses its collider and stops firing for five seconds. During the final 0.7 seconds its bones gather back into place, then its body and firing cycle return. Surviving arrows already in flight remain dangerous. A sword dropped on death returns to its pickup. Undo restores durability, inventory, facing, pickup ownership, arrows, throws and the skeleton recovery timer; reset restores both items and the living archer. Equipment and mob meshes are cached and reuse the existing opaque pass.

Z restores the complete movement gesture: all participating creatures, crate position and state, deformations, death state, portal locks and lift height/target/timers. Reset returns the crate to its terrace and lifts to their lower position. Cube maps support multiple walkable surfaces per column, tunnels and floating platforms; the original legacy chamber retains its existing layout. Stepping down onto a lower supported surface lands safely, while a fall into a true hole still kills and respawns the creature.

## Physics

soft-body.js uses a rounded 4 by 4 by 4 node lattice per creature: 64 shared nodes, 27 cells and 162 tetrahedra. It runs at a fixed 120 Hz. Cell and tet co-rotational shape matching supplies elasticity; XPBD signed-volume constraints resist compression and recover inversion; edge strain projections bound extension. Softness changes elastic stiffness instead of scaling a shader wobble.

Gravity, platform contact, static/kinetic friction, wall contact and symmetric node-to-oriented-rounded-body contacts deform the nodes themselves. Opposite contact corrections transfer motion to the neighbouring solid, with tangential contact friction. Internal damping separates center-of-mass and angular velocity from elastic motion; floor angular resistance is handled separately. Calm bodies sleep without node jitter and wake for controls, pokes, approaching moving neighbours or lost support. Heavy landings dissipate deformation rather than applying a rubber restitution impulse.

This remains a small CPU XPBD solver with finite iterations. Creature-to-creature collision uses fitted rounded OBB proxies, not an exact deforming triangle-to-triangle narrow phase. The controller drives the centroid velocity. level-features.js supplies shared height-aware surfaces, solid floor sides, moving-platform carry, lethal triggers, cyclic portal chains and snapshots. Cube columns index all their surface heights: contacts choose support below the body's feet, while separate cube AABBs provide walls and ceilings. A roof does not teleport a creature onto its top. Falling bodies can contact lower floors and land; respawn preserves the spawn's storey and checks overhead clearance. Static block collider data is cached separately from moving features.

Body contacts remain active in the falling state. Vertical contacts use a consistent upward normal and separation of the lattice bounds to prevent embedded bodies. Supported bodies become grounded on other dynamic bodies. Carrier motion is applied once, from the bottom of a stack upward, while passenger input remains relative to its carrier. Jelly and crates can each support the other; passengers can walk off and fall independently. Crates share the contact/gravity solver with a global rigid shape projection, allowing contact torque, tipping and airborne rotation while retaining their shape. Their angular motion is damped more strongly on the ground than in the air, and grounding follows actual node contact rather than a fixed upright height. Rendering transforms both positions and normals by the fitted physical orientation. Undo restores that orientation immediately and reset returns the crate upright. Crates do not trigger portals or spike deaths.

physics.js retains the original rigid solver as an independently tested baseline; the running game attaches the soft-body System and delegates all physical stepping to it.

## Graphics

The HUD has a single speaker icon toggle, compact character rows and keyboard shortcut legends. Permanent gameplay explanations have been removed; live state announcements remain available to screen readers. Elevator slabs retain their lit trim without side guide posts.

webgpu-renderer.js is a raw WebGPU/WGSL renderer with no Three.js:

The current art direction follows the cosy fantasy-dungeon concept: one warm stone palette for floors and walls (walls slightly darker), chunky bevelled blocks, warm torch pools against a cool moonlit fill, glassy jelly and readable glowing interactive elements. Weathered bronze and oak decks with rivets remain on bridges/lifts. Automatic banners and gear reliefs have been removed. Banners can return as explicit editor decorations later; gears are reserved for future gameplay mechanisms. The compact game HUD uses parchment tones and aged-bronze borders. Physics, colour identities and level layouts remain shared with the editor.

- Masonry uses a dedicated `stoneFS` pipeline. Blocks have flat faces with narrow rounded bevels. Baked per-vertex voxel occlusion darkens contacts, and faces pressed against another block render as deep mortar. The painted atlas becomes relief through a screen-derivative surface gradient; side faces get two courses of one to three stones with deep joints, lit top edges and per-stone tone. Worn, lighter bevels, dark chips and moss in cracks, joints and edges complete it. The broad moss pattern is baked per vertex, so the pixel shader only evaluates the crack mask.
- Lighting: cool sky ambient and a moonlit key with PCF shadows, warm torches with a two-frequency flicker, and each jelly's coloured transmission pool plus a glowing footprint outline projected onto the actual floor beneath it. Body and torch loops exit early and avoid dynamically indexed local arrays, which were slow on integrated GPUs.
- Torch flames are animated camera-facing billboards above glowing coals, drawn additively at the end of the opaque pass so jelly refraction still sees them.
- The scene clears to zero alpha; the post pass paints an indigo sky only where nothing was drawn, keeping full-screen work out of the MSAA and refraction buffers. Everything below the lowest floor fades into the same void colour.
- Bloom: a soft-threshold prefilter reads the HDR scene into quarter resolution, followed by a four-level dual-filter down/up chain. Idle finish runes keep a neon glow; portals, beams, flames and glints bloom.
- Jelly: glassy rounded edges located through the rest-space face grid, a tight glint instead of a whole-face flare, slightly lower absorption, light pooling near the base and seven glossy bubbles of varied size.
- Decor is scattered deterministically by cell: pebbles and rubble against walls, bones, at most two skulls, up to two spent arrows near archers and up to four cobwebs in inner corners. Cells with spawns, goals, mechanisms, crates, pickups or drones stay clear. Decor has no colliders, shares the static buffer after the masonry and is excluded from the shadow pass.
- The per-jelly key hints use the jelly colour for key borders, glow and a pointer under the “Move” caption.

Wall torches are placed explicitly from the editor's Decor palette. Click a stone cube's side face to attach one, or choose north/east/south/west in the brush and inspector; up to four different faces of one cube may carry lights. The `torches` collection stores the supporting block's integer X/Y/Z and `face`. The bracket, handle, bowl, flame, light and editor picking share the same mount transform. Torches have no physics or projectile colliders and coexist with other objects; only their supporting stone blocks remain solid. Moving, removing, undo/redo and JSON persistence work independently of the host. Missing hosts are reported by validation. Old narrow-wall torch records migrate onto the nearest existing masonry mount when loaded, and the original chamber's four lights are explicitly mounted on its side walls. Torch meshes are cached and rendered in the existing pass.

Crystal drones hover in place, with a broad, flat-faceted translucent crystal, reflective edges, a visible luminous heart and a bronze cage. The shell uses two alpha-blended surfaces in the existing sorted transparency layers, without extra refraction texture copies. Place one from Objects in the 3D editor, then set beam colour, target (a character identity or the nearest living jelly), base X/Y/Z and hover height in its inspector. They may float over empty cells without creating support blocks. The optional `drones` collection stores `{x,y,z,color,target,hover}`; colour is a hero slot 0–4, target is -1 for nearest or a hero slot, and hover is 0–6 units of extra lift (default 0). At zero the crystal centre is base Y + 0.64, leaving a 0.08-unit gap beneath its lower tip; aiming, picking, placement outlines and stone validation share this offset. Old files without drones load unchanged. Validation catches missing named targets and crystals inside stone. The original chamber includes a low-hovering green drone at (2,0,6), targeting green. Beams have a thicker luminous core, soft glow and moving, piecewise-linear lightning strands. Their kinks taper to zero at both endpoints so the visible beam remains attached to its emitter and the exact occlusion point; these cosmetic strands do not change hit detection. The core fades smoothly at both ends; actual hits add a round bright contact flare with a soft halo in the same instanced draw. Reduced motion freezes the energy flow.

A drone continuously aims directly at its target in 3D. The beam ends at the nearest solid surface, raised terrain, bridge, lift, crate, archer or jelly, including colour-filter glass. Torch decorations do not occlude beams. Matching-colour jellies are immune and can shelter others; any other jelly hit shatters and respawns through the normal death lifecycle. Contact with solid objects sprays short glowing sparks; contact with a jelly sprays droplets of its own colour, including immune jellies. These bounded particles fall and fade, with fewer and shorter effects under reduced motion. Shields protect against arrows; colour determines laser immunity. No target means no beam. Editor preview shows the same clipped beam without applying damage. Cached drone bodies share the existing opaque pass; beams use one bounded instanced draw and a brief fading afterglow on lethal hits. They add no jelly refraction passes or additional render targets. Undo/reset clears derived rays, visual afterglows and contact particles.

- The entire dungeon, characters, skulls, bubbles, plates and walls are 3D geometry with a depth buffer.
- Stone boxes sample one of sixteen chipped, cracked slab textures; wood boards and diagonal crate braces use oak grain fixed to local UVs. The crate has metal corner plates and raised rivets on all six faces. Both sRGB textures and their mipmaps are uploaded once; the existing cached geometry and prop upload buffer are reused during movement and tumbling.
- Only lattice node positions are uploaded for deforming jelly. A GPU compute pass embeds a smooth rounded surface in the lattice and transforms normals with the cofactor of its deformation Jacobian.
- Per-creature back-face passes supply exit positions and material thickness. Front-face passes bend the view ray and sample the previously rendered layer. Rendering the farther creature first supplies up to four screen-space refraction layers, sorted in full 3D so stacked creatures retain the correct order. GPU colour metadata preserves each character's pigment when earlier colours are absent.
- Beer-Lambert absorption deepens the core colour; thin regions transmit more light. Fresnel skin, a warm overhead key, a back strip and cool fill give crisp candy highlights. Skull motion has its own slower internal spring.
- Ivory dice pips are anchored to the lattice's rest coordinates and stretch with the body. Each creature carries all six values: top/bottom 1/6, +Z/-Z 2/5 and +X/-X 3/4, with opposite faces adding to seven. The front and refracted far faces share the same pip function; far-face marks are attenuated through the jelly. The pips do not represent game scores. Crossed bones sit underneath the internal skull.
- Torch point lights warm nearby stone, while the creatures cast a subtle coloured light pool on their supporting platform.
- Each jelly has a separate finish tile: green at (3,2), blue at (8,3), red at (9,2). Their distinct rune glyphs are a branching staff, a crossed diamond and a lightning zigzag. The glyphs are cached 3D strokes; each glows with its own tile and rim. The bridge button at (8,2) remains independent. A matching jelly approaching its tile smoothly illuminates the tile; leaving fades that light. Vertical beams appear only when all three finish, continuing to brighten and widen while gameplay is paused by victory. Tile lighting uses cached geometry and uniform updates; the ground halos and victory beams reuse instanced quads without extra render passes.
- An activated finish also emits small glowing rune particles in its own colour and glyph. Amethyst has a purple diamond rune. Particles rise from the tile edges, sway and fade over roughly two seconds. Leaving stops emission while existing runes finish fading; the streams keep animating during victory. Symbols share the tile glyph paths and use one instanced draw in the existing effects pass, capped at 32 particles across all active finishes. Reset and undo clear them; reduced-motion mode keeps the illuminated tile without the floating stream. All participating characters must finish to activate victory beams.
- Masonry, walls and bridges cast PCF shadow-map shadows; small decor does not. Additional height-dependent coloured contact shadows approximate transmission through jelly. These contact shadows are analytic, not a separate top-down height-map solver.
- Coloured pass-through blocks use cached glass geometry and alpha blending with depth testing but no opaque depth writes or solid shadow casting. Their faces and runes are sorted with the jelly layers, so a character remains visible behind or inside the glass. Consecutive glass faces share a pass; they require no additional full-screen refraction textures or per-frame geometry rebuilds.
- HDR intermediate buffers, bloom, Khronos PBR Neutral tone mapping, vignette, 4x MSAA and final dithering.
- Subtle monochrome film grain animates at 24 Hz after tone mapping. Toggle “Film grain” in the developer panel opened with the backquote key, or tune its strength and apparent pixel size with the adjacent sliders. Reduced motion keeps the grain static; disabling it preserves the original output dithering.
- Warm floating dust drifts above exposed surfaces in the menu, game and editor preview. A deterministic set of up to 64 softly glowing sprites animates on the GPU, respects scene depth and never creates gameplay colliders. “Floating dust” in the developer panel disables it; amount and drift-speed sliders provide finer control, while reduced motion freezes its drift.
- On desktop high-density displays the compact gameplay HUD automatically scales to 1.5× or 2×. The WebGPU canvas and large menu layout keep their original logical dimensions; the developer panel becomes scrollable when its scaled controls would exceed the viewport.
- The mesh overlay draws the actual tetrahedral edges rather than a decorative grid.
- Skull, bone, bubble, crate, lift and spike geometry is built once in local coordinates. Frames reuse these meshes and one typed upload array, updating only transforms and bubble offsets. Camera rotation, physical skull motion and animated hazards keep the same appearance without rebuilding their triangles on the CPU.

The dungeon setting stays in place rather than becoming the reference's paper studio or frosted-glass dice plate. Green, saturated blue and red jelly have separate absorption colours. Refraction is screen-space: it cannot recover off-screen geometry and is an approximation for complicated overlapping surfaces, not a ray-traced global illumination solution.

The PBR Neutral formula follows the Khronos reference: https://github.com/KhronosGroup/ToneMapping/tree/main/PBR_Neutral .

## Verify

npm run check
npm test

For real GPU/browser checks, install development dependencies with npm install, keep the local server running, then run npm run test:browser. The script uses the installed Windows Chrome executable; CHROME_PATH can select another compatible Chromium executable. It launches an isolated headless browser with WebGPU enabled, never a personal browser profile.

npm run test:combat:browser additionally checks item pickup, inventory undo/reset, camera-relative equipment facing, frontal blocks, three-hit shield cracks/destruction, wood impact audio and the firing tone, physical shield bashes, sword strikes, and skeleton collapse/reassembly on the real GPU. Combat unit tests cover all four firing directions, swept collisions, walls, crates, floor heights, nearest-hit ordering, bounded projectile lifetime, throwing across a hole, blocked flight, durability and the five-second recovery clock.

npm run test:voxels:browser (also available through test:editor:browser and test:editor:3d) checks migrated stone cubes, XYZ fields, top/side placement, single-cube erase, sparse layers, live strokes, rectangle history, orbit/perspective picking, export/import/draft persistence, an actual tunnel and height-changing portal, undo/reset, narrow screens, no-WebGPU editing and a dense 1280-cube scene. tests/voxel.test.js covers serialization/migration, multiple surfaces, solid walls, tunnel traversal, falling jelly/crate landings, ceiling collisions and layer-aware mechanisms. tests/levels.test.js retains shared schema, linking, limits and reversible operation coverage. tests/editor-space.test.js verifies inverse projection and picking. A drag locks its construction plane so newly painted geometry cannot redirect the stroke.

npm run test:parties:browser paints and plays solo-purple, blue/purple duo and four-character maps, checking validation, empty editor previews, active-only physics/HUD, roster-based controls/camera, four refraction layers, rune particles, victory/reset and editor return. Node tests cover every control set for each solo colour, every two-colour pair and its shared bindings, three/four-player ordering, marker pairing, old map compatibility, layout-independent input and the fourth character's respawn.

npm run test:conveyor:browser checks belt painting, direction/speed properties, draft persistence, connected GPU geometry, jelly/crate transport, countersteering, undo and reset. tests/conveyor.test.js also covers smooth entry and seams, all four directions, floor heights, walls, sleeping crates, stacked passengers, falls and older map compatibility.

npm run test:color-blocks:browser checks all four coloured stone tools, XYZ/face/rectangle placement, inspector recolouring, history, persistence/export, keyboard traversal by every matching hero and collision with another colour on the real GPU. tests/color-blocks.test.js covers all sixteen hero/block combinations (including sparse parties), support/ceiling filtering, crates, actual swept arrows, spawn validation and respawn.

npm run test:glass-blocks:browser compares actual rendered pixels with a jelly behind glass, behind opaque stone and inside its matching glass block. It also checks rebuilding transparent geometry and all four camera rotations in both projections without GPU errors.

npm run test:dice renders the production pip shader onto all six faces, counts the separate dots from a GPU readback and checks the 1–6 values and opposite-face sums. It also captures the three actual jelly creatures at four camera rotations. Audit images are saved in artifacts/.

Node tests exercise gameplay, all three physical keyboard layouts, three-rune puzzle completion, pushing, terrain, gravity and respawn, plus real lattice deformation, volume preservation, inversion recovery, strain bounds, heavy landing, sleeping, wall contacts, rigid-motion preservation and full-state undo. Stacking tests cover high-speed landings, jelly/crate support in either order, a three-body moving stack, independent passenger movement, crate drops and lift passengers.

The browser suite compiles WGSL on an actual WebGPU device, checks GPU validation errors, exercises all camera angles, movement, pushing, poking, lattice display, layered refraction, fall/respawn, stacked jelly carrying, lift boarding/upper exit/empty return, crate pushing/drop/undo, spike death and scraps, height-changing portal traversal and effects, the collider toggle, separate finish tiles, matching tile illumination/fade, rising rune streams and victory beams. It also checks the speaker icon toggle, compact HUD, narrow-screen layout and the no-WebGPU card. Screenshots are saved to artifacts/. npm run profile:browser records a separate CPU/frame profile. FPS depends on the adapter, viewport, browser and number of awake solids; 60 FPS was observed at rest in an earlier development headless run.

npm run profile:compare compares three creatures with two visible creatures, disables prop generation and simulation separately, and samples one awake jelly. It records per-frame CPU physics, prop preparation and total render submission time, plus a Chrome CPU sample profile, in artifacts/performance-current.json. PERF_LABEL changes the output suffix. The prop-cache change reduced measured idle prop preparation from about 34 ms to about 5 ms per frame at 1440 by 1000 in the development headless browser. Headless frame pacing and GPU/driver limits mean its FPS is not directly interchangeable with an interactive browser's FPS.
