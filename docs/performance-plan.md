# План оптимизации производительности

Рабочие заметки, октябрь 2026. Цифры получены в headless Chrome на машине разработки (1440×1000, карта «Затонувшее святилище» без дрона). Сравнивать их стоит между собой, а не с FPS в обычном браузере.

## Как мерить

- `npm run profile:solver` — физика в Node без браузера. Печатает отпечаток симуляции и мс на шаг. Если отпечаток изменился, скрипт падает: значит, оптимизация поменяла поведение физики.
- `npm run profile:compare` — браузерные сценарии (все спят, без пропсов, без симуляции, одна желейка движется, все движутся) и горячие функции CPU. Результат пишется в `artifacts/performance-current.json`. Нужен запущенный `npm start`.
- `npm run profile:browser` — короткий замер одного сценария.

## Сделано

**Солвер желе без временных массивов** (`src/world/soft-body.js`). Функции `volume`, `shape`, `strain`, `summarize`, `orientation` и `det` переписаны на скалярах. Порядок операций сохранён, поэтому отпечаток совпадает бит в бит.

| Сценарий | До | После |
| --- | --- | --- |
| Все желейки движутся: FPS | 20 | 46 |
| То же: физика, мс/кадр | 34 | 5.7 |
| Один шаг физики в браузере, мс | 6.3 | 2.2 |
| Один шаг в `profile:solver`, мс | 5.7 | 1.85 |
| Время `npm test`, с | 32 | 13 |

До оптимизации игра входила в «спираль смерти»: шаг (6.3 мс) вместе с рендером не укладывался в кадр, и за кадр делалось до 5.5 шагов вместо 2. Сейчас — около 2.5.

## Дальше, по приоритету

### 1. Пропсы каждый кадр: 7–9 мс даже в покое

Это главный оставшийся расход: без генерации пропсов рендер занимает ~6 мс вместо ~13–16 мс.

- `props()` (`src/renderer/props.js`) переиспользует готовые меши, но каждый кадр трансформирует на CPU все вершины всех пропсов в `propData` и целиком загружает буфер через `writeBuffer`.
- Варианты:
  - пропускать куски, у которых трансформация не изменилась (спящие тела, статичные кнопки и предметы), и загружать только изменённые диапазоны;
  - лучше — перенести трансформацию на GPU: меши пропсов загрузить один раз, а каждый кадр передавать только матрицу на кусок (instance-буфер или storage-буфер с индексом куска в вершине).
- Начать с замера: какие виды пропсов дают больше всего вершин (`piece.kind` и `piece.data.length`).

### 2. Мосты пересобираются каждый кадр

- `bridges()` (`src/renderer/scene.js:262`) вызывается из `render()` (`src/renderer/renderer.js:916`) и каждый кадр заново строит доски через `bridgeOakPlank` и `box`. В профиле покоя заметны `box`, `oakPlank`, `bridges` и `normalize`.
- Построить меш моста один раз в локальных координатах и каждый кадр менять только поворот вокруг петли, как уже сделано для кнопок и лифтов. Как минимум кешировать меш, пока `progress` не изменился.

### 3. Остатки в физике (после пунктов 1–2)

- `pair()` создаёт массивы на каждый узел (`sub`, `mul`, `d.map`, `mv`) — те же приёмы, что в `volume`.
- Финальный цикл `step()` по узлам (пересчёт скоростей, инерция, демпфирование) создаёт массивы на каждый узел, хотя он и выполняется один раз за шаг.
- `collisionBoxes().filter(...)` вызывается для каждого тела на каждом шаге; `heightAt` — для каждого узла на каждой итерации.
- После каждой правки проверять `npm run profile:solver` (отпечаток) и `npm test`.

### 4. Мелочи

- `getBoundingClientRect` каждый кадр в UI (заметен в профиле покоя) — возможен вынужденный пересчёт раскладки.

## Отложено: SIMD / WebAssembly

Обсуждали и решили не делать сейчас. В JS SIMD нет; WebAssembly SIMD доступен, но требует сборки и копирования данных между JS и Wasm каждый кадр, а у тела всего 64 узла. Основной выигрыш дало устранение аллокаций. Возвращаться к этому стоит, только если после пунктов 1–3 физика снова станет узким местом. Тогда сравнить два пути: Wasm SIMD с раскладкой данных по координатам (все X, все Y, все Z подряд) и перенос солвера в WebGPU compute, который проект уже использует.
